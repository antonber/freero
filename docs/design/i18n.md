# Interface languages (#5; the marketing site's hreflang is #77)

Status: **built** — the pipeline, ten languages and the language picker; what is still English
is listed at the end ("What remains"; the check keeps hard-coded text from growing).

## What we want

People use Freero in their own language: the dashboard, the board chrome, menus, toasts, dialogs,
emails and notifications, with numbers, dates and plurals the way their language writes them.
They choose it in their account (it follows them to every device), the browser's language is the
default, and a link can ask for one (`?lang=de`). Right-to-left languages mirror the chrome.

What a board *says* is never touched: switching language changes the interface around the board,
not a single element, collection or setting in it.

Languages: English (source), German, French, Spanish, Portuguese (Brazil), Japanese, Korean,
Simplified Chinese, and the right-to-left Arabic and Hebrew (`LOCALES` in `@freero/shared`).

## Library: a small ICU formatter of our own, in `@freero/shared`

`packages/shared/src/i18n.ts` parses and formats **ICU MessageFormat** — the format every
translation tool (Weblate, Crowdin, Lokalise, Pontoon) and FormatJS understand — for the subset an
interface needs:

```
Hello {name}                                  arguments
{count, plural, =0 {No votes} one {# vote} other {# votes}}
{place, selectordinal, one {#st} two {#nd} few {#rd} other {#th}}
{role, select, editor {can edit} other {can view}}
{total, number}  {total, number, percent}  {when, date, medium}  {when, time, short}
'{' quoted '}'                                apostrophe escaping, '' for a literal '
```

The locale data is the platform's: `Intl.PluralRules` (so Arabic's six plural forms, Japanese's
one, Polish's few/many all just work), `Intl.NumberFormat`, `Intl.DateTimeFormat`,
`Intl.RelativeTimeFormat`, `Intl.ListFormat`. Parsed messages are cached.

Why not a library:

- **`@freero/shared` stays dependency-free [P1]**, and the formatter must live there: the server
  words emails and notifications with the same messages and rules as the browser.
- FormatJS's `intl-messageformat` (BSD-3, allowed) is the closest fit, but brings its full ICU
  skeleton parser (~15 kB gzipped) for features we don't use; i18next (MIT) uses its own plural
  convention (`key_one` / `key_other`) unless a plugin adds ICU, and its React bindings exist to
  re-render on a language switch, which we don't do (see "Runtime").
- The formatter is ~300 lines with tests on the parts that can break (plural selection per
  language, `#`, nesting, escaping). The catalogues are standard ICU, so moving to
  `intl-messageformat` later is a drop-in change of one function.

## Catalogues: one per owned unit, next to its code

Every unit that shows text owns its messages, so a feature stays self-contained and no central
catalogue grows [Dune 4]:

```
features/<name>/messages.ts          reserved file:  export const t = defineMessages('features/<name>', en)
features/<name>/locales/en.json      the English source — the only place English text lives
features/<name>/locales/de.json      translations, one file per language
engine/messages.ts + engine/locales/            the board chrome the engine draws
ui/messages.ts + ui/locales/                    the design system's own words (Close, Search…)
app/messages.ts + app/locales/                  the shell: board page, share dialog, components
app/pages/<page>/messages.ts + …/locales/       each page area (dashboard, account, auth, admin…)
apps/server/src/modules/<m>/messages.ts + …/locales/    a module's emails and notifications
```

- **Namespace = the unit's path** (`features/voting`, `app/pages/dashboard`). The checker fails
  when `defineMessages('…')` names another path, so a copied file can't read someone else's keys.
- **Keys** are camelCase, optionally grouped with dots (`share.copyLink`). The English text is the
  value. A key is the unit's own: features never read other features' messages (W3 already forbids
  importing them).
- **Locale files** are flat JSON (`key → ICU message`), the format translation tools import and
  export. One reserved entry, `"@@unreviewed": [keys…]`, lists machine translations no person has
  checked yet (see "Translations").
- `t` is typed by the English JSON (`keyof typeof en`): using a key that isn't in English fails the
  typecheck, and the checker reports it with a better message.

## Runtime (web)

`@ui` exports the message layer (`ui/i18n.ts`): `defineMessages`, `getLocale`, `isRtl`,
`formatNumber`, `formatDate`, `formatTime`, `formatRelative`, `formatList`, `formatBytes`.

```ts
// features/voting/messages.ts
import { defineMessages } from '@ui';
import en from './locales/en.json';
export const t = defineMessages('features/voting', en);

// anywhere in the feature
t('votesLeft', { count })            // "{count, plural, one {# vote left} other {# votes left}}"
```

**The language is fixed for the life of a page.** `main.tsx` decides it, loads its catalogue, sets
`<html lang dir>`, and only then imports the app. Every `t()` — including labels evaluated when a
module loads (`defineCommands`, `defineTool`) — sees the final language, so nothing needs hooks,
context or re-render plumbing, and a component can't show half its strings stale. Changing the
language saves it and reloads the page, as most large apps do. (`?lang=` takes effect the same way.)

Loading: English is bundled with the code that uses it (each `messages.ts` imports its `en.json`).
The other languages are discovered by `app/i18n/catalogs.ts` — a discovery root like
`app/board/features.ts`, with the one `import.meta.glob` for `**/locales/*.json` — and
`vite.config.ts` puts each language's files into one chunk (`locale-de-….js`), fetched once at
start. A missing translation falls back to English for that key.

## Plurals, numbers, dates

Never build a plural with `n === 1 ? '' : 's'` or a number with `toFixed`: put the count in the
message (`{count, plural, …}`) and format numbers and dates with the `@ui` helpers or the ICU
`number` / `date` / `time` arguments, which use the page's language. `app/lib/time.ts` (relative
times) goes through `formatRelative`.

## Choosing the language

In order, the first that applies:

1. `?lang=<code>` on the URL — this tab only (kept in `sessionStorage` while it navigates), never
   saved to the account. Links from a translated marketing page use it.
2. The account's language (`Account.locale`), once the account is known.
3. What this browser showed last (`localStorage`, so the first paint is already right).
4. The browser's languages (`navigator.languages`), negotiated: an exact match, then the language
   without its region (`de-AT` → `de`), then the region we ship for it (`pt-PT` → `pt-BR`,
   `zh-TW` → `zh-CN`).
5. English.

`users.locale` (a migration of `modules/auth`, the only writer) holds the account's language.
Sign-up sends the language the page is in, so the verification email is already right; accounts
from before this change have none until the app sets it once to the language it shows them (as it
does for the time zone). `PATCH /api/auth/me { locale }` changes it (Account settings → Language,
also on the sign-in and sign-up pages for people without an account, where it only changes this
browser). If the account's language differs from the one the page booted with (it was changed on
another device), the app stores it and reloads once.

## Right-to-left

`<html dir="rtl">` for Arabic and Hebrew. The chrome mirrors through CSS logical properties
(`inset-inline-start`, `margin-inline-end`, `text-align: start`, `border-inline-start` …) instead
of `left` / `right`: the toolbar moves to the right edge, the dock to the left, menus open the
other way, flex rows reverse. Icons that point somewhere (chevrons, undo / redo arrows) carry
`.fr-rtl-flip`.

**The board never mirrors.** The canvas, the world layer and every offscreen render (exports,
thumbnails) are pinned `dir="ltr"`, so element geometry and the inline layout inside elements are
exactly what they are in English, and logical properties inside them resolve to the old physical
ones. Text inside elements keeps its own direction (the content's, not the interface's).

## Server strings

- **Emails** are worded on the server in the recipient's language: the account's `locale`; for an
  address without an account (an invitation), the language of the person who sent it.
  `platform/i18n.ts` gives a module `defineMessages(import.meta.url, en)` →
  `t(locale, key, vars)`, reading `modules/<m>/locales/<lang>.json` once. `platform/mail.ts`'s
  shared footer has its own catalogue in `platform/locales/`.
- **In-app notifications** are worded when they are listed, in the reader's language.
- **Errors** keep their English `error` text and add a stable `code` (and `params` for its
  numbers): `{ "error": "Boards can have at most 50 members", "code": "members_limit", "params":
  { "max": 50 } }`. The app shows `errors.<code>` from its catalogue when it has one and the
  English text otherwise (`app/api/client.ts` builds every `ApiError` message through `app/i18n/errors.ts`, so every place that shows `e.message` gets it). Codes are added to errors people
  actually see; the rest stay English until they get one.

### Mixed deploys and old clients

Everything is additive. An old client ignores `code` / `params` and shows the English `error` as
today; a new client against an old server gets no `code` and shows the English `error`. An old
client never sends `locale` and never reads `Account.locale`. Emails for accounts without a locale
are English, as before. No message format changes on the wire for boards.

## Board content stays as written

- `t()` is only ever applied to interface text. Nothing stored in a board (elements, collections,
  settings, template content) passes through it, and no stored value depends on the reader's
  language — a switch can't change anyone's board.
- Defaults *written into* a board when someone creates something (a new vote's title, a frame's
  name) are written in that person's language and then belong to the board, like anything else
  they type.
- Templates' content (the stickies and text a template places) stays English for now; the
  gallery's names and categories are interface text.

## Tooling and the check

`npm run check:i18n` (part of `npm run check`) fails on:

- a key used in code that English doesn't have, and an English key nothing uses (a key used as
  `` t(`status.${s}`) `` counts as using every key starting with `status.`);
- a `defineMessages` namespace that isn't its unit's path, or a `locales/` folder without its
  `messages.ts`;
- a translation key English doesn't have (stale), a translation whose ICU doesn't parse, or one
  whose arguments differ from English (`{name}` translated as `{nom}` would print nothing);
- **new hard-coded interface text**: JSX text and user-facing string props (`label`, `title`,
  `placeholder`, `aria-label`, `notify(…)` …) outside catalogues. Files that still have some are
  in `i18n.baseline.json` with their count; a count may only go down (the check prints when it
  can be lowered), and a file not in the baseline must have none.

Missing translations don't fail the check (they fall back to English); `npm run i18n:status`
prints coverage and unreviewed counts per language.

`npm run i18n:extract -- <files…>` is the codemod that moved the existing strings: it wraps JSX
text, string props and template literals in `t()`, writes the keys into the unit's `en.json` and
adds the `messages.ts` import. Plurals it can't recognise are fixed by hand.

## Translations

The first translation of every key is machine-made from English (by the agent that built this),
and every key it produced is listed in that file's `"@@unreviewed"`. A person who checks or fixes
a translation removes the key from the list; `npm run i18n:status` shows what's still unreviewed.
New English keys appear in other languages as English until someone translates them; a
contributor adding a key may add the translations (marked unreviewed if machine-made) but doesn't
have to.

## What remains

The interface (dashboard, board chrome, every feature's panels / menus / toasts, account settings,
sign-in, sharing, admin console) is in catalogues and translated into all ten languages, every
translation machine-made and listed as unreviewed. Still English:

- **Sentences the code assembles from English words.** Some messages get an English word as an
  argument, so the translation reads half-English: kanban's `{noun}` (tab, view, rows, cards,
  column), swimlane's lane / phase, private mode's `{by}` ("you reveal"), report's target nouns,
  the admin console's role words, `placeOf`, scope lists and "a / an … admin", the share
  dialog's link requirements (`parts`), the walkthrough recorder's "voice", mind map's "Board
  text is passed as data …". Each needs its words moved into the message (a `select`).
- **Server text shown as-is:** the activity feed's summaries ("created this board"), the ~140
  `HttpError` messages without a `code` (tracker and AI errors among them), and these emails:
  security notices (`auth/notices.ts`), moderation notices, privacy (export / deletion), SSO
  domain control, board retention, community listings, webhook failures, workspace emails and the
  "changes on your boards" digest (`notifications/boardChanges.ts`).
- **Web leftovers:** `i18n.baseline.json` (28 strings, mostly code samples), `document.title` in
  7 pages, label arrays declared `as const`, `new Error()` texts that reach a toast, the
  analytics consent banner (`app/analytics/runtime.ts`, built without imports) and the offline
  page; ~50 `toLocaleString()` calls format in the browser's language rather than the page's.
- **Templates:** the gallery's names, descriptions and categories (`features/templates/lib/catalog`)
  and the content templates place (`specs/`), which is board content and stays English by design
  until templates get per-language content.
- **Parsers that only know English:** text-to-kanban and the CSV importer recognise English status
  words and column names; the translations keep those words in their samples.
